# ADR-0013: Interface languages (English default, Polish second)

- Status: Accepted (PR merge, 2026-11-14)
- Date: 2026-11-14
- Related: 04 §1 (interface languages), 04 §2 (store time), 04 §14 (accessibility), ADR-0006 (frontend and session)

## Context

The owner decided that the application is available in two languages, English by default and Polish as the second
language. Until now every UI text was hard-coded in Polish in the Next.js pages, components and server actions.
The app has about 150 texts, two languages and no translators; texts change together with the code in the same PR.
Store data (store names, products, ad names) is shown as entered and is not translated.

## Decision

1. **No i18n library.** Texts live in two TypeScript catalogs, `frontend/src/i18n/en.ts` and `pl.ts`. The English
   catalog defines the `Messages` type; the Polish one is typed as `Messages`, so a missing or extra text fails
   `pnpm typecheck`. Maps keyed by API codes (statuses, error codes, health reasons) use `satisfies Record<Code,
   string>`, so a new code in the generated OpenAPI types fails the type check until both languages have a text.
   Interpolation is a plain function in the catalog (for example `saveFailed(requestId)`).
2. **Choice in a cookie, English by default.** The locale is read only from the `op_locale` cookie (`en` or `pl`);
   anything else, including no cookie, means English. `Accept-Language` is not used, so the default is the same for
   everyone. The cookie is a preference, not a secret: `SameSite=Lax`, `Secure` on HTTPS, one year. The value is
   validated against the locale list before it is stored and when it is read.
3. **No locale in the URL.** Store paths stay `/stores/:storeId/:section` (04 §2). Switching the language is a
   server action that sets the cookie and re-renders the current page, so the section and the store are kept.
4. **Server and client.** Server components and server actions call `getMessages()`; client components call
   `useMessages()`, which reads the locale from a provider set in the root layout. `<html lang>` follows the
   locale. Dates use `Intl.DateTimeFormat` with `en-GB` or `pl-PL` and always the store's time zone.
5. **Switcher placement.** A button with the other language's name (in that language) in the header next to
   sign-out, and on the sign-out page. It is a plain form, so it works without JavaScript.

## Alternatives considered

- **next-intl or a similar library.** Gives ICU plurals, locale routing and message extraction. Rejected for now:
  two languages and a small set of texts do not need it, and locale routing would change every store URL. If
  plurals, more languages or external translators appear, the catalogs map one to one onto JSON messages.
- **Locale prefix in the URL (`/en/stores/...`).** Good for public, indexed pages; this app is private and behind
  sign-in, and the prefix would complicate the proxy matcher, `returnTo` and store switching.
- **`Accept-Language` detection.** Rejected because the owner set English as the default.

## Consequences

- Every new UI text needs an English and a Polish entry; the type check enforces it.
- The Polish catalog and the Polish assertions in the e2e test are the only Polish content in the code, by design.
- Texts generated by the backend (for example the baseline decision summary) are in English. When the UI shows
  them, it should render from reason codes and values through the catalogs, not show the backend sentence.
- The language is per browser, not per user account. Storing it in the user profile can come later with settings.

## Verification

- `src/i18n/messages.test.ts`: English is the default, both catalogs have the same keys and kinds, no empty texts.
- Playwright `e2e/sign-in-and-switch-store.spec.ts`: all flows pass in English; a new test switches to Polish on
  the Activity page, checks that the page and `lang` change and survive a reload, and switches back.
